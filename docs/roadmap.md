# NX 中间件与嵌入式后续开发安排

更新日期：2026-11-12。前置交付为 `NXTelemetryMonitor` 的 `codex/groundstation-multimode` 分支，当前进展见[开发交接文档](development-handoff.md)。

后续按“接口清点 → NX 接入 → 嵌入式接入 → 整链联调 → 水下验证”推进。上位机继续负责输入选择、轨迹规划和水平闭环，NX 统一管理通信与里程计发布，嵌入式负责实际执行与最终超时保护。阶段顺序和验收门槛如下；具体日期在确定开发人员、NX 访问方式和实机排期后落定。

## 阶段总表

| 阶段 | 优先级 | 前置条件 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| M0 运行版本与接口清点 | P0 | 当前上位机交付 | NX/MCU 版本清单、字段映射、链路与控制权决策 | 确定唯一里程计入口、串口所有者、时间域和实际执行确认来源 |
| M1 NX 中间件统合 | P0 | M0 | MAVLink 服务、里程计适配、串口适配接口、部署脚本 | PC 与真实 NX 完成两种模式与故障联调，执行端可先使用桩 |
| M2 嵌入式消息收发与状态机 | P0 | M0 的协议约定；M1 提供联调接口 | FineSUB 集成分支、C 编解码、实际动作确认、独立看门狗 | 板级收发、拒绝非法报文、去重及断联停止全部通过 |
| M3 整链台架与设备联调 | P0 | M1、M2 | PC↔NX↔MCU 联调记录、配置、固件与版本表 | 真实输入、相机、切换、重启、失联和输出方向检查通过 |
| M4 水下标定与轨迹实验 | P1 | M3 | 标定参数、重复试验数据、误差/时延报告 | 手动和自动模式达到约定实机指标，故障停止可重复 |
| M5 发布与模式扩展 | P2 | M4；扩展设计可提前准备 | 可复现部署说明、版本发布、新模式开发模板 | 新机器按文档部署成功，数据与版本可追溯 |

M1/M2 约定稳定后可分开开发，但里程计接口、动作确认语义和 NX↔MCU 时钟处理必须先一致。当前不把模拟通过等同于整链实机通过。

## M0 先固定运行版本和接口

1. 从 NX 读取实际启动命令、服务文件、Python 环境、手柄桥接、惯性里程计入口、模型和配置，记录可追溯版本或文件摘要。现有 `NXStreamer` 目录尚无独立 Git 历史，应先确定中间件代码的仓库归属。
2. 在 FineSUB 对比 `SUB` 与 `惯性里程计实验`：消息结构、轴含义、电机启停、灯光、云台、推进器分配、定深与回传状态。建立新集成分支，保留原分支作为对照基线。
3. 完成一张旧字段→新消息字段映射表，写明单位、正方向、有效性和字段实际生产者；重点核对世界速度与机体速度，避免再次变换。
4. 明确 `/dev/ttyTHS1` 只由一个进程访问，惯性里程计和视频通过接口交换数据；高频传感器链路与 50 Hz 控制循环分别调度。
5. 确定 NX↔MCU 使用的 MAVLink 子集、串口波特率及带宽预算。当前参考桥接为 115200，不能直接假设全量诊断数据以 50 Hz 发送仍有足够余量。
6. 确定 NX 时间到 MCU 时间的转换方式。若转发报文，应保留剩余有效期；MCU 不可把转发接收时刻当作新的完整 200 ms 起点。

**交付与验收：** 版本清单、字段映射、时钟方案、串口吞吐预算和动作状态来源均有记录。硬件参数尚未确定的能力不在 NX 握手中声明支持。

## M1 统合 NX 的控制与惯性里程计

建议中间件分为通信、命令状态机、里程计适配、串口适配、视频服务与运行诊断，控制数据只有一个输出入口。

- 复用本仓库 dialect，实现能力握手、心跳、TIMESYNC、动作请求/确认、设定值、状态与遥测。采用 `simulated=0`，只声明实际完成的能力。
- 从惯性里程计发布位姿、速度、深度、采样序号、NX 单调源时间和 `reset_id`；采样序号在同一会话内持续递增，坐标系重置单独更新 reset ID。
- 手动与轨迹模式接收同一种归一化机体指令，统一检查会话、代次、序号、值域与剩余有效期。旧“按钮切换”语义转换为绝对目标状态。
- 对外 ACK、STATUS 必须对应实际执行状态。执行桩联调时明确标记配置；接入 MCU 后，电机启用等动作需由执行端反馈，不能仅凭 UDP 收到就返回成功。
- 保留现有 H.264/RTP 视频管线并独立管理进程，视频重启或断流不占用控制线程和串口。
- 提供启动/停止命令、服务配置、日志、参数文件和一条可复现的部署路径。NX 重启、里程计进程重启、串口重连后均保持停止，等待操作者恢复。

**验收：** 上位机连接真实 NX，执行端采用桩时即可验证“手动→轨迹→停止→手动”，并注入旧会话、乱序、重复请求、定位停更、坐标系重置、串口不可用和中间件重启。每项提供消息日志和状态变化记录。

## M2 嵌入式消息收发与执行保护

- 在 FineSUB 新集成分支引入生成的 C 头文件；串口 DMA/缓冲与解析过程应有容量和耗时边界。
- 实现协议子集和明确的应用状态机；电机启用、模式、灯光、云台和定深状态分别管理。
- 请求去重与代次检查在接收端执行，重复启用/停用不能变成再次切换。非法模式、数值越界、旧代次和 CRC 错误报文应拒绝并可诊断。
- 保留实际推进器分配算法，先确认机体正方向，再将归一化输入接入控制层。定深执行位置优先根据现有稳定实现决定；PC 只下发目标。
- 实现 MCU 独立 200 ms 指令看门狗，接收异常或指令过期清空运动与定深输出。电机停用不能因模式切换确认在途而失效。
- 回传实际应用的模式、代次、电机/灯光/定深状态与故障，NX 再据此形成面向 PC 的状态与确认。

**验收：** 共同测试向量在目标板工具链下通过；逐项测试损坏帧、分片、连续报文、重发、乱序、缓存压力、PC 断开、NX 崩溃、串口断开和 MCU 重启。记录从最后有效源指令到执行输出撤销的时间，而不只观察 PC 界面。

## M3 整链台架与设备联调

按“先观察报文与状态，再验证实际输出”的顺序联调；输出验证采用适合推进器和电源系统的台架条件。

| 检查 | 通过条件 |
| --- | --- |
| 设备映射 | 实际手柄每个轴、触发器、按钮和 hat 与已确认映射一致；拔出与重连不复用旧输入 |
| 模式切换 | 旧输出先撤销；收到对应执行确认后新模式才生效；未回中的手动接管保持停止 |
| 输出方向 | 前后、左右、偏航、上下与 FLU / 深度约定一致，三端无重复映射 |
| 实际状态 | UI、NX 和 MCU 的模式、电机与灯光目标/实际状态一致，拒绝原因可见 |
| 故障停止 | 网络、串口、定位、进程失联均清零；恢复链路不能自动恢复运动 |
| 视频与录像 | 实际 NX 视频可显示、断流恢复；本地相机与 MP4 正常退出 |
| 数据记录 | 无 Tag 仍有 NX 行；时间域、质量位、模式、源配置和版本可追溯 |

**交付：** 每条用例的结果、三端提交号/固件摘要、参数文件、日志与必要的录像。存在控制方向、超时或状态确认问题时先完成修复，再进入水下轨迹调参。

## M4 水下标定与实验

先标定归一化指令与实际速度/偏航响应，检查推进器死区、正反向差异、限幅和斜率；再调定深；随后测试短直线、侧移、原地转向，最后运行组合轨迹。

位置误差 0.15 m 和航向误差 10°目前是航点推进门限，不应直接作为整条轨迹跟踪精度的验收指标。试验前单独约定均方根误差、最大误差、重复次数、深度稳定性和链路时延要求。

每次保存轨迹 CSV、全部控制参数、NX/MCU/PC 版本、NX 数据、独立对照数据和视频。AprilTag 只用于对照分析，不反馈到自动控制；对照丢失的时间段保留质量标志。输出轨迹叠图、横向/航向误差、完成率、控制饱和占比、深度偏差和故障恢复记录。

## M5 发布与后续模式扩展

完成三端版本对应表、NX 部署/服务说明、嵌入式构建与烧录说明、协议版本策略及升级回退步骤。用干净环境检出并复现实例，再确定发布标签与是否合并主分支。

新增定点、航向保持、任务脚本或其他模态时，沿用 `enter/update/exit → Setpoint → Controller` 接口与同一通信链路。先明确输入、退出和故障条件，再补模拟测试；不修改视频和记录模块来承担控制职责。
